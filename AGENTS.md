# AGENTS.md — Контекст проекта для ИИ-агентов

Этот файл предназначен для быстрого восстановления контекста при обновлении
сессии или работе нового агента. Читай его перед началом работы.

## Назначение проекта

CLI-инструмент сборки Excel-таблицы «Трекер Актов Выполнения» для строительного
подрядчика. Данные хранятся в `database.json`, Excel генерируется из него при
каждом запуске. Мета-данные и история правок — в `_meta` (database.json) и
`changes.json` (через `wizard_git.py`).

## Быстрый старт

```bash
python3 main.py        # сборка/обновление Трекер_Акт_Выполнения.xlsx
python3 -m compileall -q -x '(^|/)(venv|\.git|__pycache__)(/|$)' .   # проверка синтаксиса
```

### Проверка синтаксиса перед запуском и коммитом

```bash
python3 -m compileall -q -x '(^|/)(venv|\.git|__pycache__)(/|$)' .
```

Команда рекурсивно компилирует все Python-модули проекта в байткод и завершается
с ненулевым кодом при первой синтаксической ошибке (файл и строка указываются).
Запускай её перед `main.py` и перед коммитом.

Зачем: Python компилирует модуль только при импорте, поэтому синтаксическая
ошибка в модуле, который не импортируется из `main.py` (например,
`wizard_edits_new.py`, `upload_to_drive.py`, `pdf_from_text.py`), проявится
только при обращении к нему — возможно, намного позже. Проверка ловит такие
ошибки сразу, не выполняя код и не трогая `database.json` и `.xlsx`.

Ограничения: команда не выявляет `ImportError`, `NameError`, ошибки типов,
логику и проблемы данных. Она может создать `__pycache__` — держи его в
`.gitignore`.

Точка входа — `main.py`. Меню-мастедакция — `wizard_edits.py` (запускается
отдельно, пункты меню: правка статусов, бюджета, документов Подобъекта,
платежей Подобъекта и т.д.).

## Ключевые файлы

| Файл | Роль |
|---|---|
| `main.py` | Точка входа: запуск сборки Excel |
| `builder.py` | Построение структуры листа Excel (строки, формулы, стили) |
| `wizard_edits.py` | Интерактивное меню правок данных + сохранение в `database.json` |
| `wizard_git.py` | Регистрация действий в `changes.json` |
| `database.json` | Единый источник данных (направления → Подобъекты → месяцы, `documents`, `payments`, `contract_sum`) |
| `config.py` | Заголовки, шрифты, заливки, границы, форматы |
| `excel_styler.py` | Применение стилей к строкам/ячейкам |
| `db_core.py` | Ядро данных: месяцы, форматирование сумм, сохранение БД |

## Критические особенности окружения

1. **`Трекер_Акт_Выполнения.xlsx` может быть открыт в LibreOffice.** Тогда
   `openpyxl.load_workbook` виснет. Проверяй результат через распаковку XML:
   ```bash
   unzip -p "Трекер_Акт_Выполнения.xlsx" xl/worksheets/sheet1.xml | \
     grep -o '<c r="E[0-9]*"[^>]*><f>[^<]*</f>'
   ```
   В книге один лист «Реестр Актов» = `xl/worksheets/sheet1.xml`.
2. **Excel-формула** записывается значением, начинающимся с `=`
   (например, `"=13+12+14"`), — openpyxl сохранит её как `<f>` в XML.
3. **`payments`** — список чисел на уровне Подобъекта; в колонку E «Оплачено»
   пишется формула-сумма в строке Подобъекта (`obj_row` берётся сразу после
   создания строки, до добавления документов).
4. **`documents`** — служебный ключ уровня Подобъекта (документы-«братья»
   месяцев), как и `contract_sum`; в списке месяцев не отображается.
5. Тестовые данные `"payments": [13, 12, 14]` для `01_271_КН` оставлены
   намеренно как демо.

## Процесс работы с Git

Полный алгоритм — в [docs/GIT_WORKFLOW.md](docs/GIT_WORKFLOW.md). Кратко:

1. **Любое изменение кода — только через ветку `feature/<название>`.**
   Это включает рефакторинг, оптимизации, исправления багов, добавление новых функций,
   мелкие правки, очистку кода и т.д. Не делать коммиты прямо в `main` без ветки —
   даже для мелких изменений.
2. Merge — только после живой проверки (запуск + верификация результата).
3. В `main` — fast-forward merge, push делается с согласия владельца проекта.
4. Ветки (локальные и remote) после слияния удалять: `git branch -d`,
   а не `-D` (защита от неслитых изменений).
5. Коммиты — в формате Conventional Commits: `feat:`, `fix:`, `docs:`, `chore:`.
6. Документацию (`.md`, описания) можно коммитить сразу в `main` без ветки.
    Исключение: если `.md` описывает код или функциональность — коммитить через ветку.
7. **После merge ветки в `main` — обновить:**
   - `changes.json` → добавить запись в `_changelog` (имя ветки, статус `merged_and_push`, дата, краткое описание)
   - `TODO.md` — перенести выполненные задачи в раздел «Завершённые задачи» с датой и списком изменений
