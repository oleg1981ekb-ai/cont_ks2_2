# Git Workflow — алгоритм слияния веток

Документ фиксирует рабочий процесс с Git для этого проекта, чтобы процесс был
воспроизводим при любой смене контекста/исполнителя. Это **источник истины** по
git-процессу; в `AGENTS.md` приведена краткая выжимка, при расхождении
приоритет у этого документа.

## Политика веток

| Тип изменения | Ветка | Merge в `main` |
|---|---|---|
| Новая функциональность, рефакторинг кода | `feature/<название>` | Да, после проверки |
| Исправление бага | `fix/<название>` (или `feature/*`) | Да, после проверки |
| Документация, не описывающая код | Можно сразу в `main` | Без ветки (соло-проект) |
| Документация, описывающая код/функциональность | `feature/<название>` или `docs/<название>` | Да, после проверки |
| Экстренные тривиальные фиксы | Допустимо сразу в `main` | С пометкой в коммите |

Правила именования:

- имя ветки — латиница, нижний регистр, дефисы: `feature/edit-payments`;
- одна ветка — одна задача; не смешивать рефакторинг, фичу и форматирование;
- коммиты атомарные: один коммит — одно логически завершённое изменение.

## Алгоритм принятия решения о слиянии

### 1. Готовность функции (главный критерий)

Merge выполняется только после живой проверки, а не «потому что код написан»:

- синтаксис всех модулей:
  `python3 -m compileall -q -x '(^|/)(venv|\.git|__pycache__)(/|$)' .`;
- запуск: `python3 main.py` завершается без ошибок;
- верификация результата: проверить сам файл Excel (см. «Проверка Excel»
  в AGENTS.md — из-за LibreOffice используем `unzip` + `grep`, а не openpyxl).
  Формула/значение в ячейке должно быть найдено физически в XML;
- регрессия данных: структура `database.json` не потеряла направления,
  Подобъекты, месяцы, `documents`, `payments`, `contract_sum` и `_meta`;
- сгенерированные `.xlsx` изменились только там, где ожидалось.

> Если результат не подтверждён — merge преждевременен, даже если «вроде работает».

### 2. Границы изменений

```bash
git status --short
git diff --stat
```

- Закоммичены только файлы, относящиеся к задаче.
- Посторонние изменённые файлы — остановиться и уточнить у владельца,
  тащить их в merge нельзя.
- Отладочный код, `print`-заглушки, закомментированные блоки и секреты
  (токены, пароли, ключи) в diff попадать не должны.

### 3. Чистота рабочего дерева и резервные копии

Перед переключением веток и merge не должно быть незакоммиченных изменений:
иначе они уедут в чужой коммит или потеряются при checkout.

Перед операциями, затрагивающими данные, сделать резервную копию вне git:

```bash
cp database.json "database.json.bak-$(date +%Y%m%d-%H%M%S)"
cp "Трекер_Акт_Выполнения.xlsx" "Трекер_Акт_Выполнения.bak-$(date +%Y%m%d-%H%M%S).xlsx"
```

Резервные копии не коммитить. Если `database.json` изменён намеренно — оформить
это отдельным коммитом с понятным сообщением.

### 4. Согласование

`main` — общая ветка. Push в неё делается **только по явному согласию
владельца проекта**. Молчание ≠ согласие: согласие фиксируется явным ответом.

### 5. Подготовка перед merge

Перед слиянием ветка должна быть синхронизирована с `main` и проверена целиком:

```bash
git fetch origin
git rebase origin/main
```

- Конфликты решаем **в ветке**, а не в `main`.
- `rebase` допустим только для локальной, ещё не опубликованной ветки.
  Если ветка уже запушена, предпочтителен merge из `main` в ветку; переписывать
  опубликованную историю можно только с согласия владельца и через
  `git push --force-with-lease` (обычный `--force` запрещён).
- `git diff origin/main...HEAD` — просмотреть все изменения ветки, а не только
  последний коммит.
- В diff только файлы задачи: без `.xlsx`, `__pycache__`, `venv`, временных
  файлов, резервных копий и посторонних правок.
- `git status --short` пуст: незакоммиченных изменений нет.

Если ветка менялась после проверки — проверку повторить. Merge без актуальной
синхронизации и свежей проверки не выполняется.

### 6. Стратегия слияния

```bash
git checkout main
git merge --ff-only feature/<название>
```

- Если `main` не двигался с момента создания feature-ветки — merge будет
  **fast-forward** (линейная история, без лишнего merge-коммита). Это норма.
- `--ff-only` безопаснее: если fast-forward невозможен, команда остановится,
  и вы осознанно решите, нужен ли настоящий merge.
- Если `main` разошёлся — выполнить `git merge --no-ff feature/<название>`
  с осмысленным сообщением. Возникшие конфликты **не решаются молча**:
  показать владельцу варианты и согласовать.
- **`force push` в `main` запрещён** при любых обстоятельствах.

### 7. Конфликты, в том числе в данных

- Конфликт в коде: разобраться в причине, не выбирать `ours`/`theirs` вслепую.
- Конфликт в `database.json`: это данные, а не текст. Сравнить обе версии
  по смыслу (направление → Подобъект → месяц → документы/платежи), вручную
  собрать корректный JSON, проверить валидность:
  `python3 -m json.tool database.json > /dev/null`.
- После разрешения конфликта — пересобрать Excel и повторить проверки из п. 1.
- Если непонятно, чья версия верна, — остановиться и согласовать с владельцем.

### 8. Уборка, changelog и контроль

Сразу после merge (до push, если push ещё не согласован):

1. Обновить `changes.json`: запись в `_changelog` (ветка, дата, описание).
   Статус `merged_and_push` ставить только после фактического push;
   до него — `merged`.
2. Обновить `TODO.md`: выполненные пункты перенести в «Завершённые задачи».
3. Закоммитить эти изменения как `docs: update changelog and TODO ...`.

Затем:

```bash
git push origin main
git branch -d feature/<название>             # -d проверяет, что ветка слита
git push origin --delete feature/<название>  # если ветка выгружалась на remote
git status --short --branch   # дерево чистое, main синхронен с origin/main
git branch -a                 # лишних веток нет
git log --oneline -3          # нужные коммиты на месте
```

Почему `git branch -d`, а не `-D`: флаг `-D` удалит ветку даже неслитую —
это защита от потери работы. Ошибка `remote ref does not exist` при попытке
удалить remote-ветку не критична: она означает, что ветка на remote никогда
не выгружалась.

### 9. Откат после merge

- Обнаружена ошибка в `main` — откатить обычным коммитом:
  `git revert <sha>` (не `reset --hard` и не force push).
- Ошибка затронула данные — восстановить `database.json` из резервной копии
  или из предыдущего коммита, затем пересобрать Excel и проверить результат.
- После отката — снова пройти проверки из п. 1 и зафиксировать причину
  в `changes.json`.

## Формат коммитов

Conventional Commits:

- `feat: <что добавлено>` — новая функциональность
- `fix: <что исправлено>` — баг-фикс
- `docs: <что описано>` — только документация
- `chore: <что сделано>` — обслуживание (удаление веток, настройки)

Пример: `feat: платежи Подобъекта — формула суммы в колонке E`

## Чек-лист перед merge (копировать в задачу)

- [ ] Ветка названа по правилам, одна задача — одна ветка
- [ ] Коммиты атомарные, сообщения по Conventional Commits
- [ ] Резервная копия `database.json`/`.xlsx` сделана (если менялись данные)
- [ ] Ветка синхронизирована с `main` (`git fetch` + `git rebase origin/main`)
- [ ] Правило rebase опубликованной ветки соблюдено
- [ ] `git diff origin/main...HEAD` просмотрен полностью
- [ ] В diff только файлы задачи, без `.xlsx`/`__pycache__`/секретов
- [ ] Код компилируется (`compileall` по всем модулям)
- [ ] Запуск `main.py` без ошибок
- [ ] Результат проверен в XML Excel-файла
- [ ] Регрессия `database.json` проверена
- [ ] `git status --short` — только файлы задачи
- [ ] Рабочее дерево чистое
- [ ] Согласие владельца на push в `main` получено
- [ ] Merge выполнен (`--ff-only`, иначе `--no-ff` с согласованием)
- [ ] `changes.json` и `TODO.md` обновлены
- [ ] Удаление ветки: `-d` локально + `--delete` на remote (если была)
- [ ] Финальная проверка: `status` / `branch -a` / `log`
